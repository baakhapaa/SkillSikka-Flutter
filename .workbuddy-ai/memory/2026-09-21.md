## Signup: location is now filled by a popup instead of typed

**Asked for:** on the signup forms, stop asking the user to type their location —
on page open, show a popup asking to use the current location, designed to match
the app.

**Shipped:**

- `lib/core/location/location_service.dart` — new. Wraps `geolocator` +
  `geocoding`. `hasPermission()`, `detectCurrentLocation()` (service-enabled check
  → permission request → `getCurrentPosition` → reverse geocode), `openSettings()`.
  Every failure is converted to a `LocationFailure` carrying a
  `LocationFailureReason` (`serviceDisabled` / `permissionDenied` /
  `permissionDeniedForever` / `lookupFailed`) so the UI can pick the right button.
  Reverse geocode falls back to `lat, lng` — Android without a geocoder backend
  has no place name to give.
- `lib/core/widgets/location_prompt_dialog.dart` — new. `showLocationPromptDialog`
  via `showGeneralDialog` (scrim `0x66101828`, fade+scale 0.94→1, 220ms). One
  dialog, four stages: asking → loading → detected → failed. Plus `AppPalette`
  (the signup tokens, extracted), `CurrentLocationButton`, `LocationFieldHint`.
- Both signup forms: popup fires from `initState` via a post-frame callback; the
  Location field is read-only while the value came from the popup, editable after
  "Enter Manually"; gold crosshair button re-detects; helper line under the field
  shows state and a "Re-detect" link. Both pages now take an injectable
  `locationService` for tests.
- `pubspec.yaml`: added `geolocator ^14.0.2`, `geocoding ^5.0.0`. No existing
  dependency version moved.
- `AndroidManifest.xml`: `ACCESS_COARSE_LOCATION` + `ACCESS_FINE_LOCATION`.
  `ios/Runner/Info.plist`: `NSLocationWhenInUseUsageDescription`.

**Deliberate UX choice:** `_promptForLocation({bool? skipIntro})` — `null` decides
from the current permission (so a returning user isn't nagged, just auto-detected),
`true` jumps straight to detection (crosshair button), `false` always shows the
explainer (tapping an already-filled field, so the user gets a choice rather than a
silent re-scan).

**Verified:** `flutter analyze` → "No issues found!". New
`test/signup_location_prompt_test.dart` → 6/6 pass, covering popup-on-open,
detect→confirm→write-into-field→field-locks-readonly, `skipIntro`,
permission-denied-forever → Open Settings, services-off, and the manual path.

## Scope note: the location feature is client-side only, and macOS was missed

Asked whether this was frontend-only. Verified by grep: **no API, no `ApiClient`,
no `dio`, no network call anywhere in `lib/features/signup/`.** The location value
is only written into the local `TextEditingController`; neither form submits
anything (student `_submit()` just checks the ID card and pushes `/signup/verify`;
instructor `_submit()` has an explicit `// TODO: send ... to your backend`). So
this is UI + native device capability, not a data path to any server.

What is *not* fake, despite being "frontend": the OS permission prompt, the real
GPS fix, and reverse geocoding (Android `Geocoder` / iOS `CLGeocoder` — on Android
that can reach Google's backend, which is the platform's service, not ours).

**Gap found and closed after the first hand-off:** I had added Android + iOS config
only. macOS needs *two* files, and its `Info.plist` key differs from iOS:
- `macos/Runner/Info.plist` → `NSLocationUsageDescription` (iOS uses
  `NSLocationWhenInUseUsageDescription`)
- both `macos/Runner/DebugProfile.entitlements` and `Release.entitlements` →
  `com.apple.security.personal-information.location`

All four plists now verified to parse via `plistlib`. Lesson: the geolocator
README's per-platform `<details>` blocks are easy to half-read — check every
platform the app actually targets before declaring a plugin wired.

## Fixed: section accent bar and enrollment price misalignment

**Asked for:** "the bar in front of 'explore our top instructors' is not properly
aligned and in 'get premium courses' the enrolment Rs 24.99 is also misaligned",
with a cropped screenshot as the reference.

**Root cause, both cases — geometry left to font metrics.** The bar was a
`Text('|')` in a 21pt Manrope font: its line box is ~28.7px tall while the 16pt
heading's cap band is only ~12.2px, so wherever the row aligned the *boxes*, the
bar's ink landed elsewhere. `_buildTopInstructors` used
`CrossAxisAlignment.end`, which put the bar's ink **3.5px above** the heading's
optical centre (measured from a rendered PNG: bar rows 760–774 centre 767 vs
heading cap-top 765 / baseline 776 → core centre 770.5). Same defect, milder, in
the `CrossAxisAlignment.center` variants.

The price had the mirror problem: two `height: 1.0` line boxes stacked with no
gap leave only ~3px of air between `ENROLLMENT` and `Rs.24.99`, which reads as a
collision (the reference has ~10px).

**Shipped:**

- `lib/core/widgets/section_bar.dart` — new `SectionBar`. An explicit
  `Container(width: 3, height: 16)` instead of a glyph, so height and position
  are declared rather than inherited. Centred against the heading's line box,
  which for Manrope coincides with the cap-height centre to within 0.0005em.
- All six `Text('| ')` headings swapped to `const SectionBar(), SizedBox(width: 7)`
  — `home_page.dart` ×3 (incl. dropping `CrossAxisAlignment.end`),
  `premium_courses_page.dart`, `recommended_course.dart` (keeps its own
  `0x1F111827` tint), `skill_courses.dart`. The 7px gap reproduces the old
  advance+space so heading text doesn't shift horizontally.
- `home_page.dart` enrollment block: `SizedBox(height: 7)` between the label and
  the price.
- `test/section_bar_alignment_test.dart` — new. `getRect` geometry assertions
  (bar centre ≈ heading centre within 0.5px; enrollment stack centred in the pill;
  label→price gap ≥ 5px). Verified it fails on the old layout: reintroducing
  `.end` produced `Actual 1676.06` vs `Expected within 0.5 of 1672.56` — the
  exact 3.5px.

**After:** bar offset −0.5px (was −3.5px); enrollment ink gaps 14px above /
14px below in the 60px pill (was 18/17 with a 3px label→price gap, now 10px).

**The reference image is not a screenshot of this app.** Its scale-independent
ratios disagree with the code: `labelToPriceGap / pillHeight` is 0.162 in the
image vs 0.067 in the render, `dividerToPillGap / pillHeight` 0.275 vs 0.20, and
the pill fill is `#F9FAFB` where the code uses `#F2F1F7`. Exact flat-area colours
prove nothing about scale — resampling preserves them — but a ratio mismatch at
any scale is conclusive. It is almost certainly the Figma export, i.e. the design
is airier than the implementation. I matched the *rhythm* (the 7px gap) and
centred properly; I did **not** change the pill fill, and flagged that to the user
as a separate call.

# Round 2: the enrollment block was width-starved, not misaligned

The user came back with "i dont think it is solved" and a **real device
screenshot** (720x1600 px = 360x800 logical at DPR 2) showing
`RenderFlex overflowed by 1.00 PIXELS` and the text wrapping as
`ENROLLM / ENT` and `Rs.24. / 99`.

**Second, independent root cause.** `SizedBox(width: 69)` between the text column
and the button. At 360pt the pill is `360 - 30 - 32 = 298pt` wide, so the text
column got `298 - 20 - 69 - 137 - 20 = 52pt` for a string that needs **72.0pt**
(measured with Inter 10pt). Hence the wrap, and a stack 62.1pt tall in a 60pt
pill. The 69pt gap was fine on the 393pt canvas the design was drawn on and
starved the label on a 360pt phone. Fixed by `SizedBox(width: 12)` + letting
`Expanded` absorb the slack → 109pt at 360pt. Also added `maxLines: 1` +
`overflow: TextOverflow.ellipsis` to both texts, and removed the outer
`mainAxisAlignment: MainAxisAlignment.center`.

So the two rounds were genuinely different bugs: round 1 was vertical font-metric
alignment, round 2 was horizontal width starvation. Both were real; the user only
ever saw round 2.

**Scale calibration of the device screenshot (this is the useful part).**
`ENROLLMENT` (Inter 10pt) measures 15 device px of cap band → 7.5pt, matching
Inter 10pt's 7.27pt cap at 2 px/pt. The pill measures 592x120 px → 296x60pt,
matching the code's 298x60. So the screenshot is definitely 2 px/pt and the
code's sizes are confirmed. The pill fill is exactly `#F2F1F7` — i.e. the *code's*
value, unlike the first reference image's `#F9FAFB`, which is further evidence
that image 1 was the Figma export and image 2 is a real device capture.

**Unresolved:** the section heading in that same screenshot measures an 8pt cap
band, where Manrope 16pt should give 12pt. Everything else in the image matches
the code exactly, so the heading alone does not. Not explained; not load-bearing
(the heading the user complained about, "Explore our Top instructors", is not in
that screenshot). Worth re-measuring if it ever comes up.

## Harness notes worth keeping

- `matchesGoldenFile(finder)` walks **up** to the nearest repaint boundary, so
  the capture came back as a shifted crop with a transparent left margin.
  Wrapping the page in an explicit keyed `RepaintBoundary` fixes it.
- Goldens are always **DPR 1** regardless of `tester.view.devicePixelRatio`, so
  compare against a DPR-2 screenshot by upscaling the golden ×2.
- `flutter test` loads no bundled fonts, so `Icon` renders as a **tofu box**
  unless MaterialIcons is registered by hand from
  `build/unit_test_assets/fonts/MaterialIcons-Regular.otf`. Proved with a bare
  `Icon` control capture — not a layout bug.
- Pre-warm **all nine weights including `w900`** or `google_fonts` throws
  `Inter-Black was not found`. It only surfaced once something forced a
  re-resolve, which made it look like an unrelated regression.
- Scroll with `ScrollableState.position.jumpTo`, not `drag`: drags clamp at the
  extents and a "drag by the delta" loop never converged. And target a pinned app
  bar's clearance (~68pt), or the heading lands under the bar.
