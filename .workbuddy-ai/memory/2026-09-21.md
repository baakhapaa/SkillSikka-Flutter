## Signup: location is now filled by a popup instead of typed

**Asked for:** on the signup forms, stop asking the user to type their location —
on page open, show a popup asking to use the current location, designed to match
the app.

**Shipped:**

- `lib/core/location/location_service.dart` — new. Wraps `geolocator` +
  `geocoding`. `hasPermission()`, `detectCurrentLocation()` (service-enabled check
  → permission request → `getCurrentPosition` → reverse geocode), `openSettings()`.
  Every failure is converted to a `LocationFailure` carrying a
  `LocationFailureReason` (`serviceDisabled` / `permissionDenied` /
  `permissionDeniedForever` / `lookupFailed`) so the UI can pick the right button.
  Reverse geocode falls back to `lat, lng` — Android without a geocoder backend
  has no place name to give.
- `lib/core/widgets/location_prompt_dialog.dart` — new. `showLocationPromptDialog`
  via `showGeneralDialog` (scrim `0x66101828`, fade+scale 0.94→1, 220ms). One
  dialog, four stages: asking → loading → detected → failed. Plus `AppPalette`
  (the signup tokens, extracted), `CurrentLocationButton`, `LocationFieldHint`.
- Both signup forms: popup fires from `initState` via a post-frame callback; the
  Location field is read-only while the value came from the popup, editable after
  "Enter Manually"; gold crosshair button re-detects; helper line under the field
  shows state and a "Re-detect" link. Both pages now take an injectable
  `locationService` for tests.
- `pubspec.yaml`: added `geolocator ^14.0.2`, `geocoding ^5.0.0`. No existing
  dependency version moved.
- `AndroidManifest.xml`: `ACCESS_COARSE_LOCATION` + `ACCESS_FINE_LOCATION`.
  `ios/Runner/Info.plist`: `NSLocationWhenInUseUsageDescription`.

**Deliberate UX choice:** `_promptForLocation({bool? skipIntro})` — `null` decides
from the current permission (so a returning user isn't nagged, just auto-detected),
`true` jumps straight to detection (crosshair button), `false` always shows the
explainer (tapping an already-filled field, so the user gets a choice rather than a
silent re-scan).

**Verified:** `flutter analyze` → "No issues found!". New
`test/signup_location_prompt_test.dart` → 6/6 pass, covering popup-on-open,
detect→confirm→write-into-field→field-locks-readonly, `skipIntro`,
permission-denied-forever → Open Settings, services-off, and the manual path.

## Scope note: the location feature is client-side only, and macOS was missed

Asked whether this was frontend-only. Verified by grep: **no API, no `ApiClient`,
no `dio`, no network call anywhere in `lib/features/signup/`.** The location value
is only written into the local `TextEditingController`; neither form submits
anything (student `_submit()` just checks the ID card and pushes `/signup/verify`;
instructor `_submit()` has an explicit `// TODO: send ... to your backend`). So
this is UI + native device capability, not a data path to any server.

What is *not* fake, despite being "frontend": the OS permission prompt, the real
GPS fix, and reverse geocoding (Android `Geocoder` / iOS `CLGeocoder` — on Android
that can reach Google's backend, which is the platform's service, not ours).

**Gap found and closed after the first hand-off:** I had added Android + iOS config
only. macOS needs *two* files, and its `Info.plist` key differs from iOS:
- `macos/Runner/Info.plist` → `NSLocationUsageDescription` (iOS uses
  `NSLocationWhenInUseUsageDescription`)
- both `macos/Runner/DebugProfile.entitlements` and `Release.entitlements` →
  `com.apple.security.personal-information.location`

All four plists now verified to parse via `plistlib`. Lesson: the geolocator
README's per-platform `<details>` blocks are easy to half-read — check every
platform the app actually targets before declaring a plugin wired.

## Follow-up: "Enter Manually" removed — field is typeable again

User asked to drop the manual-entry option. I asked what should happen to the
field when detection fails, because the button was also the unlock mechanism;
they chose **"stay typeable"**. Result:

- Popup stages are now: `asking` → `Allow Location`; `loading` → `Cancel`;
  `detected` → `Use This Location` + `Detect Again`; `failed` → `Open Settings`
  (blocked) / `Turn On Location` + `Try Again` (services off) / `Try Again`.
- `Cancel` during loading is mine, not theirs — a 20s GPS wait with zero buttons
  felt broken. Flagged it in the reply; easy to drop.
- **API simplified:** with one success outcome left, `LocationPromptResult` and
  `LocationPromptOutcome` were dead weight. `showLocationPromptDialog` now returns
  `Future<DetectedLocation?>` — non-null = confirmed fix, `null` = dismissed.
- Failure copy no longer says "you can still enter it yourself" — states the
  problem, buttons offer the action.
- Both pages: `_locationDetected` state, the read-only lock, and the tap-to-reopen
  wiring are gone. The Location field is a plain editable input again, the
  crosshair button is always shown, and `LocationFieldHint` lost its params
  (static one-liner, no "Re-detect" link).
- Tests updated + extended to 7, including a new `hang: true` fake that holds the
  loading stage open to assert `Cancel` exists and no manual option does. That
  test must **not** use `pumpAndSettle` — the spinner animates forever.

`flutter analyze` clean; 7/7 pass. Grep confirms no residual references to the
removed option outside the tests that assert its absence.
